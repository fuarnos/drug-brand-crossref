## 3. 唯一需要知悉的点：i18n WARN 55

FAIL 0，但有 55 条 WARN，构成为：

| 规则 | 条数 | 判定 |
|---|---|---|
| `pseudo-suspect`（es, LABEL_I18N） | 2 | **既有**（`form.kit='kit'`、`form.gas='gas'`，v0.11.3 就有） |
| `hardcoded` | **53** | **误报**，见下 |

53 条 `hardcoded` 全部落在 **法语词典自身**里：

```
归属顶层变量确认：L1021 / L1120 / L1183 → FR_I18N
                  L1348                → FR_PREP_KEYS
样例：'voir tous sur la fiche du principe actif' / 'France' / 'Licence Ouverte / etalab-2.0'
```

根因：`deploy/i18n_check.py` 的 `LANGS = ("en", "es", "zh", "zh-Hant")` **还没有 `fr`**
（实测该文件里 `'fr'` / `"fr"` 均不存在）。于是检查器把法语字面量当成「未翻译的英文」报警。

**根因不在「语言表没跟上」，而在硬编码检查的 AST 解析。** 详见 §3.1（已修，WARN 55 → 2）。
`fr` 目前**仍未**进入键集一致性校验，原因见 §3.2。

### 3.1 已修：`check_hardcoded` 认不出这两张译文表

`deploy/i18n_check.py` 的 `check_hardcoded()` 靠「顶层赋值语句的行号区间」来判断一段字面量是不是译文表：

```python
for node in tree.body:
    if not isinstance(node, ast.Assign):   # ← 只认 `X = {...}`
        continue
    ...
    if target.id.endswith("_I18N") or target.id == "I18N":
        dict_spans.append(span)            # 落在这些区间里的字面量不检查
```

而 v0.11.4 新增的两张法语表都不匹配：

| 常量 | 写法 | 为什么没被认出来 |
|---|---|---|
| `FR_I18N`（build.py:907） | `FR_I18N: dict[str, str] = {` | 是 `ast.AnnAssign`（带类型注解），被 `isinstance(node, ast.Assign)` 直接跳过 |
| `FR_I18N.update({...})`（:1118） | 函数调用，不是赋值 | 同上，没有 span |
| `FR_PREP_KEYS`（:1344） | `FR_PREP_KEYS: dict[str, str] = {` | 名字不以 `_I18N` 结尾，即使无注解也不匹配 |

于是这 53 条法语译文被当成「模板里的裸文案」报 WARN。

**修法**（只改 `deploy/i18n_check.py`）：

1. 新增 `HARDCODED_DICT_NAMES = {"FR_PREP_KEYS"}` + `_is_i18n_dict_name()`；
2. `check_hardcoded()` 同时接受 `ast.Assign` 与 `ast.AnnAssign`；
3. 额外把 `X_I18N.update({...})` 这种调用也计入字典区间。

**验证**：

| 项 | 改前 | 改后 |
|---|---|---|
| FAIL | 0 | **0** |
| WARN | 55（53 → hardcoded） | **2**（只剩既有 `es form.kit` / `es form.gas`） |
| INFO | 21 | 21（不变） |

变异测试（证明规则没被削弱）：把 `--build-py` 指向一份合成 build.py，内含
`<p>This sentence is hardcoded and should be flagged</p>`，仍然报 `[hardcoded]` 1 条。

> `--self-test` 在本机跑不了：sandbox 拒绝 `os.chmod`（`PermissionError: [WinError 5]`，与
> Chrome/CDP、命名管道同源），属既有环境限制，与本次改动无关。已用上面的变异测试替代。

### 3.2 没改 `LANGS`：加 `fr` 会直接让门禁变红

任务书建议「把 `fr` 加进 `LANGS`」。实测**不能这么做**——在内存里把 `LANGS` 扩成
`("en","es","zh","zh-Hant","fr")` 后跑同一份 `run()`：

```
现状（无 fr）  : FAIL 0  / WARN 55
若加 fr 到 LANGS: FAIL 19 / WARN 56
新增 FAIL 规则  : {'dict-no-lang': 18, 'release-latest-incomplete': 1}
```

原因：`check_dicts()` 对 `I18N_DICTS` 里的 18 张字典逐个断言「每种 `LANGS` 语言都必须在表里」
（`if lang not in table: out.add("FAIL", "dict-no-lang", ...)`）。这 18 张字典都是
`{key: {en, es, zh}}` 结构，**没有任何一张有 `fr` 表**，加进 `LANGS` 就等于给每张表判一个 FAIL。

所以 `fr` 要真正接进门禁，前提是先把法语数据装成「每字典一张 fr 子表」的形状，
这需要一个**形状归一化层**（`FR_I18N` 是扁平的 `key → 法语文案`，共 555 键，不是嵌套结构），
并且要先补齐与 en 的差距。当前实测差距：

```
FR_I18N 555 键 vs I18N.en 240 键
fr 缺 en：home.fr、nick.source（2 个）
fr 多出 en：317 个（about.* / coverage.* 等，属合并后的其它字典，非陈旧）
FR_PREP_KEYS 3 键，值是对 FR_I18N 的覆盖，键不全在 FR_I18N 里
```

**结论**：本轮只修了误报（WARN 55 → 2，FAIL 0），**fr 的键集/伪翻译校验仍未启用**，
建议单开任务：归一化 FR 表 → 补 `home.fr` / `nick.source` → 再把 `fr` 加入 `LANGS`。
否则现在把 fr 写进 `LANGS` 只会让 `ci_checks --fast` 立刻变红。
