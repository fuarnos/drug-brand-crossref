## 4. 补丁过程中的一个问题（已修）：行尾被改成 CRLF

`.tmp/ko_merge.py` 用 `Path.write_text()` 写文件；Windows 上 `newline=None` 会把 `\n` 翻成 `\r\n`。

- `site/build.py`、`data/languages.json` 原本就是 CRLF → 无影响（diff 全是真实改动）。
- `deploy/i18n_check.py` 原本是 **LF**（1,333 行）→ 补丁后整文件 1,402 行全变 CRLF，`git diff --stat` 一度显示 **2,735 行**。
  已用字节级替换转回 LF：

```powershell
& $py -c "from pathlib import Path; p=Path('deploy/i18n_check.py'); b=p.read_bytes(); p.write_bytes(b.replace(b'\r\n', b'\n'))"
```

复检：`CRLF=0 / LF-only=1333+`，`git diff --stat` 回落到 **121 行**（+95/−26），内容未变。
**后续教训**：一次性补丁脚本在 Windows 上写 LF 文件要显式 `newline="\n"`；本仓 `site/build.py` 仍是 CRLF，改它时保持原样即可，别顺手统一。

### 10.5 方案取舍（② 为什么选构建期复制而不是 JS 兜底）

Lead 允许两选一。这里选**构建期英文复制**：
- 客户端兜底要按「容器」分组判断缺块，而 name 页 / maker 页有**多个块组共用一个父节点**，按父节点分组会误判（该显示的组被隐藏），风险高；
- 构建期复制是确定性的，`(EN)` 语义与既有 `_warn_lang_blocks` / `_atc_source_html` 的标注习惯一致；
- 代价：以后新增语言时，I18N 驱动的块自动有内容（①），**数据型块需再补一次兜底或补译**——已写进本报告。
