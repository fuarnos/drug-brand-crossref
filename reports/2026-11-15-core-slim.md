> 任务：I8/T38（task-10）· 工位 page-slim · 目标 **raw ≤ 40 MB / gzip ≤ 9.5 MiB**，且搜索与页面行为逐项不变。

## 3. 做法（`site/build.py`：`encode_core()` + 新增 `_slim_core_cols()` / `_client_slug()`）

**编码格式升到 `v: 2`**（`CORE_VERSION = 2`），顶层新增 `"mk": [[厂家名, slug], …]`；解码端 `decodeCore()` 输出的条目字段名/含义与 v1 完全一致，`render()` 以下逻辑一行没改。

1. **`ml` → 全局厂家表 + id 数组（-6.44 MB）**
   `ml` 是「+N 其它厂家」链接表：`[["石家庄四药有限公司","maker-…"], …]`。15,199 个不同数组里共出现 203 万次「厂家对」，其中只有 **14,521 个唯一厂家对**。改为：`mk` 存全局表一份，`ml.d` 存 id 数组，`i` 仍是每行字典下标。
   > 订正 Lead 交接里的一处口径：`ml` 不是「市场数组」，实测是厂家链接数组；市场数组是 `c`（`["CN","TW"]`，741,738 B，已字典压缩）。
2. **`u` → 客户端推导 + 稀疏例外（-1.91 MB）**
   `u` 就是 `key_file(k)`（name 页文件名，含中文、只替换路径非法字符）。客户端加 `slugFile()` 复刻同一套正则，逐行算 `u`；只额外存两份稀疏数据：
   - `ux`：无 name 页（`u == ""`）的 132,668 个行下标；
   - `uxv`：客户端算不出来的 1,032 行例外值（键 >80 字符要走 md5 后缀、astral 字符、异常空白）。
   构建期判定用的是 `_client_slug()`（**客户端真能算出的值**），不是 `key_file()`——第一版用 `key_file()` 判定，1,032 行 md5 后缀被误判成「可推导」，被 §5 的逐行比对抓到并已修正。
3. **`t` / `nc` / `eo` → 位掩码 `fl`（-0.87 MB）**
   三个 0/1 列合成 `fl = t | nc<<1 | eo<<2`；`decodeCore()` 拆回 `e.t / e.nc / e.eo`，条目不新增 `fl` 字段。
4. **试过但否掉的方案**（避免后面重复试）
   - `c` 市场数组 → 13 位位掩码：741,727 → 762,787 B（**更差**）；
   - `d` 字典列：6,251,333 → 6,984,000 B（展示名基本唯一，**更差**）；
   - `dp` 字典列：raw -356 KB，但 gzip **+11 KB**（模式串重复度高，字典下标反而更难压）；
   - `u` 稀疏表带值（`{"i":…,"d":[…]}`）：1.26 MB，换成「默认推导 + 只存下标」后 0.86 MB。

## 4. 兼容策略（`v` 升级 + 老缓存）

- **格式自描述**：`core.v` 1 → 2，`decodeCore()` 同时能解 v1 和 v2（v1 的 `u/t/nc/eo` 是普通列，走通用分支）→ **新 HTML + 旧缓存 core 不会半破**。
- **新客户端守卫**（`loadMainIndex()`）：拿到 core 先校验 `c.v === CORE_V(2)`；不符先带 `&r=<timestamp>` **cache-bust 重拉一次**；仍不符 → 试 `legacy-mini.json`（同为 v2）；再失败抛错，走既有「加载失败 + 重试按钮」UI。错版本的 core 绝不会被拿去渲染。
- **反向窗口**（旧 HTML 内联/外链的旧 `app.js` + 新 core）：旧 JS 里加不了版本守卫。`BUILD_V` 是 `build.py` 内容哈希，新 HTML 一定带新 `?v=`；静态站 HTML 缓存与资源 TTL 同量级（10 分钟），窗口内老页面可能表现为「登记详情」链接缺失/`t` 缺失 → 刷新即恢复。这是任何 core 结构变更都有的窗口，和 v0.11.2 那次加列同类。
- **构建期守卫照旧**：`CORE_FIELDS` 漏列 → `SystemExit` 中止构建（v0.11.2 的 `t` 事故防线未动）。
- `legacy-mini`（`WRITE_LEGACY_MINI=1`，默认关）同步升到 v2：含 `mk`，列集合把 `u` 换成 `ux/uxv` 并带 `fl`。
- **产物自检**：`.tmp/pageslim-dist/assets/app.js` 里 `const CORE_V = 2;`、`function slugFile(`、
  `data/idx/core.json?v=3700712775`（BUILD_V 已随 build.py 内容变化）、cache-bust 重试分支都在。

## 7. 缺口与后续（不是「做完就算」的部分）

1. **`json.loads` ≤400 ms 未达**：实测 525–550 ms（改前 667–685 ms）。体积 -19.2% 只换来 -18% 解析时间（CPython `json` 对这份「多字符串 + 大量小数组」的载荷近似线性）。要再进 ~8 MB 只有继续砍 `k`/`d`：
   - `d` 相对 `k` 的公共前缀/后缀差分（`d` 6.25 MB 是现在最大可动项，且 `d` 里有大量「同一商品名 + 不同规格后缀」）；
   - `ux` 从 int 列表改 base64 位串（-0.8 MB，但 gzip 可能略差）；
   - 把 core 拆成「k/d 骨架 + 其余列」两请求（要改加载与失败回退路径，风险高）。
   本轮刻意没做：在「语义完全不变」的前提下，这三项都需要额外一轮全量回归，硬塞进本轮会拉高回归风险。
2. **dist 总量已超预算**：新 1115.0 MiB / 旧 1123.8 MiB，`docs/网站优化流程.md` §2.1 的自设上限是 900 MiB（**不是本次改动造成**，旧产物就已经 1123.8 MiB）。发布前建议 Lead 重算预算或另开回收任务（combo stub 内联、厂家名折叠等既有计划）。
3. `mk` 表仍是「名字 + slug」两份字符串（815 KB）；下一步可只存 slug、名字由客户端反推（约再省 0.3–0.4 MB）。
4. 修完 §3-2 的 bug 后**已重新全量构建**（`== done ==`，`.tmp/pageslim-build2.log`），产物 core 字节与修复前重新生成的结果一致（38,670,850 B），`ci_checks --fast` 在最终产物上复跑仍 PASS 8 / FAIL 0。

## 8. 回滚方式

- **代码回滚**：`git checkout -- site/build.py`（本轮只改这一个文件），重跑 `& $py site/build.py` → core 回到 v1（raw 47.89 MB / gzip 10.21 MiB）。客户端 **不需要**回滚（`decodeCore()` 同时兼容 v1）。
- **不要只回滚 core.json**：新版 HTML 的守卫要求 `c.v === 2`，单独把 v1 的 core 换回去会触发「版本不符 → cache-bust 重拉 → 报错 + 重试」，页面不渲染。回滚必须「代码 + 重建」一起做。
- 发布前建议保留本版 `site/dist/data/idx/core.json` 与 `site/dist/assets/app.js` 各一份到 `data/backups/`（人拍板），便于紧急比对。
