## 2. 三个真正的拦路问题（比改代码更关键）

1. **工作区有别的会话在改东西。** `git status` 里有 `docs/每日开工卡.md`、`docs/谷段需求队列.md`、`etl/markets/`、若干 reports 未提交。`site/build.py` 目前干净、可以改；但**全量建站会把那些会话的产物差异一起烘进 `site/dist`**，而且 §7 规定同一时间只许一个会话建站。→ 开工前要么等它们收尾，要么只做「改 + 单页验证」不上全量构建。
2. **zh-Hant 生成链在 `.tmp`。** 任何新键都必须同步进繁体，否则 `i18n_check` FAIL（"缺译不许静默回落英文"是用户 2026-11-10 定的规则）。生成器在，能跑；但它不在仓库里，属于必须补的技术债。
3. **build ≠ 上线。** 建站只改 `site/dist`，线上靠 `deploy/publish.ps1`（唯一入口）。要真正让用户看到，需要 CHANGELOG 加一节 + build 到 `== done ==` + publish + `verify_live.py --expect-version` + tag/Release。这一步是发布决策，不是改代码决策。

## 3. 成本与批次建议

| 批次 | 内容 | 建站次数 | 预计时长 | 说明 |
|---|---|---|---|---|
| **Batch 1** | P1-1a + P1-1b + P1-1c + P3 | 1 次全量 | 40–60 min | 纯文案/属性，零功能面；风险最低，收益最直观（三语承诺一致 + 读屏语言正确） |
| **Batch 2** | P1-2 + P2-3 + P2-3b | 1 次全量 | 40–60 min | 有回归面，单独提交便于回滚 |
| **Batch 3（需拍板）** | 1280 视口 + zh-Hant 生成器入库 | 0–1 次 | 30 min | 改口径 / 改工具 |

单次全量验证清单（§5 要求）：`site/build.py` 到 `== done ==` → `first_screen_check.py` 改前/改后各一次（至少 home + drug + atc）→ 三语各抽 3 条检索 → 页数 / 索引大小 / 首屏体积回归 → 链接 / 404 / sitemap 抽检 → `detect` 复扫。
