## 3. 清单 A：精度归整建议（`precision_normalize_20261114.csv`）

### 3.1 规则（写死在脚本常量里）

* **档位** `PRECISION_TIERS` = 10 / 20 / 25 / 40 / 50 / 100 / 125 / 200 / 250 / 300 / 400 / 500 / 600 / 750 / 800 / 1000（16 个）。
  只认标签上真会出现的整数强度，所以 `0.005 mg`、`2.5 mg` 这类合法小剂量不会被卷进来。
* **双阈值**：`|v − 档位| ≤ 0.01`（绝对值）**且** `|v − 档位| ≤ 档位 × 0.01%`（相对值），并且 **`v ≠ 档位`**（正好整齐的不需要建议）。
* 不做四舍五入兜底：不命中就一行不出。`force_round` 那种「所有非整数一律取整」被明确排除——全库非整数强度 97,230 条，
  绝大多数（12.5、0.375、0.005…）是真实剂量。
* 输出**只有** `suggested_display` 是建议值；`strength_value` / `per_volume_*` 全是 `repr(float(...))` 的原值。
  数据包、索引、入库值都不动。

### 3.2 SQL

预筛（让 SQLite 先砍掉 97% 的整数行；任何档位命中都必然满足这个不等式）：

```sql
SELECT pc.product_id, pc.ord, v.substance_id, s.inn_en, p.country,
       pc.strength_value, pc.strength_unit, pc.per_volume_value, pc.per_volume_unit
  FROM product_component pc
  JOIN product   p ON p.product_id = pc.product_id
  JOIN variant   v ON v.variant_id = pc.variant_id
  JOIN substance s ON s.substance_id = v.substance_id
 WHERE pc.strength_value IS NOT NULL
   AND pc.strength_value > 0
   AND ABS(pc.strength_value - ROUND(pc.strength_value)) <= 0.01   -- 参数 = PRECISION_ABS_TOL
 ORDER BY p.country, pc.product_id, pc.ord
```

档位与相对阈值在 Python 侧判（`match_tier()`），这样档位表就是唯一的、可解释的规则来源。

复核 triage §1.5 基线（现查，未变）：

```sql
SELECT COUNT(*) FROM product_component pc JOIN product p USING(product_id)
 WHERE ABS(pc.strength_value-500) < 0.01 AND pc.strength_value <> 500;   -- 41
```

## 4. 清单 B：名称-规格冲突（`name_spec_conflict_20261114.csv`）

### 4.1 判定式（T10 §6.1 口径）

**只有「同一个 name_key 下所有单方产品共享唯一 `(strength_value, strength_unit)`」的键才参与判定。**

```
键可判定 ⟺ len({ (strength_value, strength_unit) | 该键下的单方产品(component 数 == 1) }) == 1
```

多规格键一律排除 —— 例：`panadol` 键下 13 个产品 / 4 个规格（160/325/500/1000 mg），
朴素做法会把 `PANADOL TABLET 500 mg`（实际挂在 US-0135-0537 的 160 mg 液体上）报成「名说 500、结构化 160」，是假阳性。

在这条门槛之内，逐条比对名称：

| # | 处理 | 例子 |
|---|---|---|
| 1 | 只取 `name_type='trade'` 的名称（含非 primary；不限文字体系） | — |
| 2 | 解析名称里的「数字 + 单位」，单位族 = `mg / g / mcg / ml / l / iu / ui / %` | `1 g` ↔ `1000 mg`、`500 microgram` ↔ `0.5 mg` |
| 3 | 同族换算到量纲基准后比数值（质量→mg、体积→mL、活性→IU、百分比→%） | `2,5 mg` = `2.5 mg` |
| 4 | 数字多解析：空格/逗号既是千分位也可能是小数点，还可能是品牌编号，**所有解析都算候选** | `1 000 mg`、`5,000 microgram`、`CACIT VITAMINE D3 500 mg` |
| 5 | 紧跟 `/` 的数字是浓度分母，不参与比对 | `500 mg/100 g`、`150 mg/1.5 mg per g` |
| 6 | 容差与清单 A 一致：`≤0.01` 或 `≤0.01%` 算一致 | `100 mg` ↔ `100.008 mg` 不会两边同时记账 |
| 7 | 名称量纲与结构化规格量纲不同 → 跳过（不判冲突） | 名称 `70 %` vs 规格 `mg` |

再排除三类「同一支药、不同计量基准」（**会单独计数打印**，属精度取舍，不是判定式的一部分）：

| 排除 | 例子 |
|---|---|
| 结构化强度带盐型 / 水合物 / 酯（`variant.salt|hydrate|ester` 非空） | `terbinafine 250 mg` ↔ `281.25 mg` |
| 名称自己声明了另一基准（`(as hydrochloride)`、`equivalent to …`） | `pantoprazole (as sodium sesquihydrate) 40 mg` |
| 名称用 `+` 枚举多个规格（组合装 / 起始装 / 套装） | `5mg+10 mg+15 mg+20`、`15mg patches + 2mg gum` |

**复方产品（component ≥ 2）不在本口径内**：它们的「自身规格」不是单一值，按 §6.1 不参与唯一规格键的定义。
实测这类「名称 token 对不上自身任一成分」有 **3,719 行**（AU 2,058 / CA 729 / US 252 / SG 218 / GB 201 / FR 146 / ES 112 / MX 3），
其中包含真问题（如 `Motival 10mg/500microgram`、`Exforge HCT 5/160/12.5`），**备查、不入本 CSV**；要覆盖请另立口径。

## 5. §1.4「法国 250 mg 片剂下出现名称 1000」复核

### 5.1 我方 SQL 与结果（**复现，不是 0 行**）

```sql
SELECT DISTINCT p.product_id, nv.raw, pc.strength_value
  FROM product p
  JOIN product_component pc ON pc.product_id = p.product_id AND pc.strength_value = 250
  JOIN product_name pn ON pn.product_id = p.product_id AND pn.name_type='trade' AND pn.is_primary=1
  JOIN name_variant nv ON nv.key_id = pn.key_id
 WHERE p.country='FR' AND p.form_base='tablet'
   AND replace(replace(replace(nv.raw,' ',''), char(160), ''), char(8239), '') LIKE '%1000%';
-- → 15 行
```

放宽验证：`FR`（任意剂型）+ 有 250 mg 组件 + 名称含 1000 → 19 行；`FR` + tablet + 名称含 1000（不看组件）→ 170 行。
命中的 15 个产品全是 LEVETIRACETAM / KEPPRA / NAPROSYNE / EFFERALGANMED / LEPTAX 这类「一个 CIS 码打包多个规格」的品牌。

> triage 记的是「精确 SQL 0 命中」。我没有拿到 triage 的原始 SQL，无法逐字比对；最可能的原因是
> **去掉空格之后再匹配带空格的 `'1000 mg'`**（法语写法是 `1 000 mg`，去空格后是 `1000mg`，含空格的模式永远匹配不上），
> 或额外要求了「名称唯一挂在一条产品上」。我这边只用可复核的 SQL 说话：**子串口径 15 行**。

### 5.2 为什么会看到这个现象（根因）

以 `FR-60044784` 为例（现查）：

```
name key = "levetiracetam viatris comprime pellicule"（该 key 被 3 个产品共用）
  raw: LEVETIRACETAM VIATRIS  250 mg, comprimé pelliculé
  raw: LEVETIRACETAM VIATRIS  500 mg, comprimé pelliculé
  raw: LEVETIRACETAM VIATRIS 1000 mg, comprimé pelliculé
component: ord 0 = 250 mg（Levetiracetam）
```

即：**FR 的一个 CIS 码把 250/500/1000 三个 presentation 收成了一条产品记录，三个写法都挂在同一个名称 key 上**。
按 250 mg 分组展示时，这条记录连同「1000 mg」的名称一起出现在 250 mg 组里 —— 用户看到的正是这个。
这是**名称层（名称 ↔ presentation 挂接）** 的问题，不是「结构化强度算错了」。

### 5.3 这一类的规模，以及为什么 CSV 不收它

把 §1.4 写成通用判定（不写死 250/1000）：**名称 token 对不上本产品，但能对上「同一个名称 key 下的兄弟产品」**：

* 名称 token 对本产品冲突：**89,059 行**
* 其中 token 能对上同 key 兄弟产品强度：**74,828 行（84.0%）**；按国家 AU 18,159、GB 16,005、CA 12,583、FR 9,144、US 7,129、ES 6,859、SG 4,588、MX 289、CN 72

74,828 行 ≈ 全部名称行的 17%，是**系统性挂接问题**，不是 v0.11.6 能在显示层逐条消化的量；
按 T10 §6.1，这类键正是「多规格键」，必须排除（`panadol` 反例同理）。
所以 §1.4 的 15 行**不在 CSV 里**——它要的是名称层修复（拆 presentation / 按强度拆 key），
把它塞进「规格待核实」小清单反而会掩盖真正的原因。**建议 Lead 把 §1.4 另立一条任务（名称层），不算进 T15。**

| 包装体积 / 净含量 | `Byetta … 2.4 ml ↔ 0.04 mL`、`Zolgensma 8.3 ml ↔ 5.5 mL`、`CHOLESTYRAMINE 378 G TIN ↔ 444.4 mg` | ~4/40 | **误报**（名称是包装量） |
| 浓度 / 剂型错配 | `CLOPINE TAB 100MG ↔ 50 mg/1 mL`、`Acetylcysteine 600 ← 200 mg` | ~2/40 | **误报**（名称为每片量、结构化是浓度） |
| 真的对不上 | `Chlorpropamide 100 ↔ 250`、`Azathioprine 25 ↔ 50`、`SIMVACOR 40 ↔ 10`、`MEDOVIR 200 ↔ 400`、`MICTONORM 15 ↔ 30`、`DAFLON 1000 ↔ 500` | ~11/40 | **真候选** |

**结论：清单 B 是「高召回、低精度」的候选集（40 条抽样里 29 条属基准/口径差，约 7 成）。**
比旧口径（不限唯一规格键，90% 误报）明显收敛，但仍**不能**直接当显示层告警用。

**T10 决定（2026-11-14 Lead 已确认，并写进 T10 任务）**：冲突徽标**不全量启用**，
只做「机制 + 默认关闭开关」；**在补齐 `variant.base_fraction` / `salt_code` 之前不打开**。
理由：现库 14,244 个 variant 的 `base_fraction` **全是 1.0**、只有 2,163 个有 `salt`，占大头的盐基/元素量误报压不下去；
`data/salt_base_fraction.csv` 只有 `fraction_rule` 公式、缺每个成分的分子量，**没法自动算**，属新数据工作。
