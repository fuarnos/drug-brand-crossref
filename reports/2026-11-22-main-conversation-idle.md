# 主对话默认空闲：答完即停 + 禁止自唤醒（2026-11-22）

## 结论

用户 2026-11-22 提出「主对话还是经常无法保持空闲」。查证后落地 5 处改动（**纯文档 / prompt，无代码、无构建、无发布、无写库**）：
主对话（对接会话）收到用户消息后 **回答 + 登记即结束本轮**，不再「先回话、再继续手上的活」；
「队列里还有待办」「工位还在跑」不再算继续干活的理由；对接会话**禁止**自建 schedule / spawn teammate / 起后台 job。

## 根因（为什么之前几轮都没解决）

1. **规则没限定会话类型**：`docs/工作组与流程.md` §三写着「工位在实现期间，Lead **必须并行推进不冲突的事**」——
   在对接会话里也照做，于是主对话永远在找活干。
2. **「无事即停」的触发条件永远不成立**：原文是「没有用户消息、没有后台任务、**也没有待办要推进**时」才停；
   项目队列永远有待办 → 这条规则实际上从不生效。
3. **用户在谷段会话里聊天**：00:30 每天新建一个会话，用户在最新会话里说话（`docs/交接-20261122.md` §2：
   01:26–02:10 的四组消息就落在谷段会话）。旧规则「先回话 + 登记，**再继续手上的活**」让它答完继续交付 → 不空闲。
4. **自我唤醒**：开工卡要求会话开工时自建 08:20 的 at 收尾提醒；会话一旦「开工」过，就会在 08:20 被自己叫醒。

## 四、追加（2026-11-22 截图）：真正占住会话的是 `wait_agent`

用户随后发来 GUI 截图：`等待子智能体 · {"timeout_ms": 420000}` → `深度求索中，用时 3 分 22 秒`。
这说明「主对话不空闲」的直接机制不是「在干活」，而是 **Lead 在等工位**——等待期间会话被占住，什么都不产出。

- **根因**：旧规则「`wait_agent` 单次 ≤5 分钟、连续 ≤2 次」把长等待**合法化**了；而这次 `timeout_ms=420000`（7 分钟）
  连旧上限都超了。等待本身不产生进度，工位完成本来就会以消息开新一轮。
- **改动**：
  1. `AGENTS.md` §12 新增「**禁止 `wait_agent`**」：派单 / 发消息 / 起后台任务后**结束本轮**；看进度只做一次事实查询
     （`list_agents` / `team_task_list` / `git diff --stat` / `reports/` 时间戳），不设 `timeout_ms`；旧「≤5 分钟 / ≤2 次」作废。
  2. `docs/工作组与流程.md` §三 两条改写：禁用 `wait_agent`；删掉「最多等 1 个工位」的兜底。
  3. `docs/每日开工卡.md` 硬规则补「禁止 `wait_agent`」。
  4. `.dsh/preset-drug/cordis.patch.yml` persona 补「不等待子智能体」。
  5. 00:30 prompt 增加第 4 条同义约束。
- **验证**：`schedule_view` 新 prompt 已落；文档三处读回一致。**行为验证**：下一次交付会话若派单后**不再出现** `wait_agent` 调用、
  且工位回报能自动开新一轮，即通过（可在 GUI 的「正在调用工具」里直接看）。
- **风险**：如果某个工具链确实需要「立刻拿到工位结果」，正确做法是**等它的回报消息**，不是阻塞等待；
  若发现回报没有唤醒会话（DSH 行为异常），再回退到「≤60 秒单次等待」并在报告记录。
