## 4. 异常与偏差

### 4.1 dist 体积比 Lead 报的少 60,559 B

- Lead 口径：121,450 文件 / **901,613,979 B**；本工位实测：121,450 文件 / **901,553,420 B**（Δ **−60,559 B**，−0.007%）。
- 文件数完全一致、版本与 sitemap 数一致；delta 量级约等于一个中等 HTML 页面。
- 最可能原因：Lead 的数字取自 `site/build.py` 收尾时点，之后 `deploy/publish.ps1`（gh-pages 侧，
  见 §4.2）在 **10:37:23–10:37:28** 往 dist 根写了/替换了几个文件（`404.html`、`checksums.txt`、
  `.nojekyll`、`robots.txt`、`sitemap.xml`、sentinel）。
- **不影响上传正确性**：上传的就是冻结后的这份 dist，且与桶的 check 为 0 differences。

### 4.2 dist 根多了一个 sentinel 文件（不是我们写的）

- `site/dist/e2fea3dfe91d65e7c4dc23106afa53e2.txt`（41 B，内容是一串 40 位十六进制）+
- `.tmp/publish-opt/gh-pages-cache/` 里有**同名同内容**的文件 → 来自 gh-pages 发布流程（pages-deploy 工位）的
  cache-busting sentinel，被写进了 dist。
- 处理：**原样上传**（它就是冻结 dist 的一部分）；如果 Lead 认为该文件不该在主域存在，
  下一版可让 publish.ps1 只在 gh-pages 侧写、不落 dist。

### 4.3 `verify_live` 唯一失败项 = 护栏口径，不是站点问题

| 证据 | 值 |
|---|---|
| HTTP | **200**，`content-type: application/json`，`content-encoding: gzip` |
| 头部 | **无 `Content-Length`**；`transfer-encoding: chunked`；`etag: W/"558be898…"`；`last-modified: 2026-11-11T18:52:14Z` |
| 实际传输 | 9,816,074 B（wire，gzip） |
| 解压后 | **42,801,654 B，与本地 `site/dist/data/idx/core.json` 逐字节相同** |
| gzip -9（解压后重压） | **9,801,041 B** → 落在护栏 **2.5–12 MB** 区间内 |
| `verify_live.py:268-274` | 该检查读 `Content-Length`；R2/Cloudflare 对 gzip JSON 用 chunked → 取不到 → FAIL |

→ 结论：**内容、体积、可访问性全部正常，失败是检查脚本假设「响应一定带 Content-Length」。**
