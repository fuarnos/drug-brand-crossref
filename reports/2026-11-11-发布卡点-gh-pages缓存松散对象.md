# 发布卡点：gh-pages 缓存松散对象爆炸（v0.11.1）

日期：2026-11-11 · Lead · 状态：修复中

## 1. 现象

`deploy/publish.ps1` 在 v0.11.1 发布时**卡在 `git push` 的对象枚举阶段 1 小时 50 分**：

```
==> [312s] Committing changes on top of gh-pages
6c7d6da56 Publish v0.11.1 (121450 files, incremental)      ← 本地提交已生成
git.exe ... push --progress origin                          ← 一直停在
Enumerating objects: 147,790 …（数字缓慢增长，约 22 个/秒）
```

- 远端 `gh-pages` 仍停在 `6946d8e42`（v0.11.0）→ **没有半推**，中断安全。
- 上一版（v0.11.0）同样流程只用了 **969 秒**，说明不是网络问题。

## 2. 根因

`.tmp/publish-opt/gh-pages-cache` 的对象仓库：

| 指标 | 值 |
|---|---|
| 松散对象 | **2,440,758 个** |
| 松散对象体积 | **4.98 GB** |
| 已打包对象 | 118,191（2 个 pack，92.6 MB） |
| 垃圾对象 | 1（`.git/objects/de/tmp_obj_la6rPn`） |

`publish.ps1` 第 320–322 行的设计是：**关掉 `gc.auto`，让增量提交累积松散对象，push 时现打 pack**。注释里预期「~60k loose objects」，实际累积到 **244 万**，是预期的 40 倍。

松散对象多了以后，`git push` 的对象枚举要对每个松散对象做一次 stat/查找（而不是查 pack 索引），于是从「秒级」退化成「每分钟一千多个」。

## 3. 处置

1. 杀掉卡住的 push（**本地提交保留**，远端无变化，重放安全）。
2. 缓存仓库 `git repack -adq --threads=4` + `git prune-packed`：把 244 万松散对象压成一个 pack。
3. 重跑 `deploy/publish.ps1`（唯一入口，不手工推 gh-pages）。
4. 发布后 `verify_live.py --expect-version v0.11.1`。

## 4. 建议（下一版落地）

给 `publish.ps1` 加一道前置守卫，避免同一问题复发：

```powershell
# 在 push 之前
$counts = & $Git -C $CacheDir count-objects -v
$loose = ($counts | Select-String '^count:').ToString().Split(':')[1].Trim()
if ([int]$loose -gt 300000) {
    Say "loose objects: $loose — running repack before push"
    & $Git -C $CacheDir repack -adq --threads=4
    & $Git -C $CacheDir prune-packed -q
}
```

阈值 30 万（设计预期 6 万的 5 倍）留足余量；repack 一次约 10–20 分钟，比卡两小时划算。

## 5. 教训

- 「本地提交成功 ≠ 发布成功」：中断后必须 `git ls-remote origin gh-pages` 确认远端状态，再决定重放（本次远端未变，安全）。
- 发布耗时要记录：v0.11.0 = 969 s，v0.11.1 若不修缓存会 >6,600 s。以后把「push 耗时」写进发布报告。
- `.tmp/` 里这类缓存属于**长期状态**，不是一次性垃圾；删它等于让 publish 重新全量 clone（gh-pages 单分支全量克隆，121,450 文件），别随手清。
