**规则（与方案 b 一致，最小改动）**：
- 排序仍由原键决定（`-score, -n_products, key 长度, 品牌` / ATC 大类用 `-成分产品数, -n_products`）；
- 排序后**只在「同一 key_id（同名）+ 同一 base 成分 tuple」的组内做稳定分区**：基名卡在前、盐型卡在后；
  组外顺序完全不变，盐型卡仍留在候选集里（**不合并产品、不改身份/碰撞/剂量语义**）；
- base 映射：`substance.inn_en` 去尾部盐/水合物词并迭代到不动点（13,648 行 → **834 条盐型→基名映射**），
  如 `Metformin Hydrochloride→Metformin`、`Clopidogrel Hydrogen Sulfate→Clopidogrel`、`Escitalopram Oxalate→Escitalopram`；
- 客户端镜像按条目 `e.x`（成分显示名）做同样的去盐/分组，条目仍按原键排序后再组内换位。

## 5. 性能与边界

- `SearchIndex` 装载：**0.313 s**（多一次 substance 13,648 行查询 + 834 条映射预计算）；查询期只做 dict 查表，
  trilingual 总耗时 **658.6 s**（改前 673.9 s，无变慢）。
- 规则只在「同 key + 同 base 成分组」内换位；无关卡片相对顺序逐位不变（20 条抽检为证）。
- **未做**：不改 `db/`、不改 `substance/variant`、不改页面结构/徽章、不做剂量换算；`site/dist` 未重建。
- **客户端镜像的验证缺口**：本机无 node、本任务不建站，`site/build.py` 只做了 `py_compile` + 插入块括号配平
  （brace 15/15、paren 62/62、bracket 22/22）；**浏览器端需在 pages-deploy 建站后补 5 条冒烟**
  （plavix / glucophage / cipralex / viagra / imodium 的 rank0 应出现基名）。若浏览器异常，回滚只需 revert
  `site/build.py` 的 7515-7562 / 7613-7614 两个块。
- build 层 `_sub_base_map()` 的盐词表没有 `oxalate/hydrogen`（历史口径），但客户端镜像按 `e.x` 名称剥离分组，
  不依赖索引期是否已归并；因此两处规则仍能对齐（本次未改 `_sub_base_map`，避免动索引产物）。
