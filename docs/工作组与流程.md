## 一、编制：1 个 Lead + 4 个核心工位（2026-11-20 用户重设）

> 用户 2026-11-20 原话：「lead 也就是主对话负责和我对接，一个负责找还有哪些数据可以扩展，一个负责发布……**前端和后端分开**」「当出现新的可并行程序的时候可以自主决定建立新的」「**不设立上限，按照需求增加或减少**」「剩下的我不动了」。
> 旧的 **1 Lead + 8 固定工位** 从即日起作废；固定核心只有下表 5 个角色，**工位数不设上限、按需求增减**。

| 角色 | 管什么 | 写权限（默认） |
|---|---|---|
| **Lead**（主会话） | 只对接用户：需求登记、拆解、派单、验收、汇报、对外沟通；**不写实现** | `docs/`、根级配置、需求队列 |
| **`data-scout`**（数据扩展） | 「找还有哪些数据可以扩展」：市场 / 数据源调研 → 许可核实 → 评估 → 申请信；产出落许可清单、数据源调研清单、跟进提醒 | `docs/许可清单.md`、`docs/数据源调研清单.md`、`docs/跟进提醒.md`、`data/sources/`、`reports/` |
| **`backend`**（后端） | 数据侧实现：`etl/` 入库、`db/` 库表与质量、`lib/search.py` 检索；**唯一写 `data/drugs.db`** | `etl/`、`db/`、`lib/`、`data/sources/`、`reports/` |
| **`frontend`**（前端） | 用户看到的一切：`site/build.py` 模板 / CSS / JS、九语文案、页面信息架构；**唯一改站点源码** | `site/build.py`、`site/`、`data/languages.json`、`reports/` |
| **`release`**（发布） | 生产构建 + 上线 + 线上验收：build → `sync_r2.ps1` → `verify_live` 0 failures → tag/Release；**唯一写 `site/dist` 与 R2** | `deploy/`、`reports/`（生产构建写 `site/dist`） |

**按需增减、不设上限（用户 2026-11-20 授权）**：出现**新的可并行工作**时，Lead **自主决定**新建工位（临时或长期），**不必请示用户、不设人数上限**；工作减少时同样自主收回，任务完成即退、不空养。同时并行实现任务上限仍为 **2**（WIP ≤ 2；工位多不等于并行多，串行点见 §三）。

**其余不设固定岗**：质量自查、新人走查、文档整理、只读外部调研等，按需开临时 subagent（限定写作用域，完成即退）。

**写权限是任务级的**：派单时在任务上写 `write_scopes`，冲突时以它为准（advisory，不是锁）。

### 主对话（Lead）只对接需求，不干活（用户 2026-11-13 定）

> 用户原话：「**主对话不负责干活，只负责对接需求**」。

- **Lead 做**（**谷段交付会话里**；对接会话只做「对接、登记、拆解、派单、回答」+ 只读查证，见下一条）：需求对接与登记（逐条进 `docs/谷段需求队列.md`）、澄清与拆解、派单、验收（跑检查/复核数字）、对外沟通、收尾文档。
- **Lead 不做**：写实现——页面 / 文案 / CSS / JS、`etl/`、数据加工、DB 写入、`site/dist` 构建产物、报告里的技术方案落地，全部由工位做。
- **唯一例外**：P0 热修（线上坏了、发布门槛被卡），Lead 可直接动手，但必须在当天交接里写明「为什么不是工位做、改了什么、怎么验的」。
- 与「工位不 commit / 不发布 / 不写 `site/dist`」合起来就是完整分工：**Lead 管流程与对外，工位管实现**。
- **会话类型判定（2026-11-18 用户定，方案 A；2026-11-20 结构 v2 沿用）**：只有首条消息首行带 `【谷段交付会话】` 标签、或人明确要求开工的会话才走 **6 步交付**；其余会话（含人手动新建的）是**对接会话**：只读查证 + 登记 + 拆解 + 派单 + 回答，**不 build / 不发布 / 不写库 / 不改实现 / 不开长任务**。交付会话里收到用户消息也是「先回话 + 当天登记」，**回话不等于开工**。

## 二、一次交付的标准流程（6 步，2026-11-20 起）

```
① 取活 → ② 派单 → ③ 实现 + 自验 → ④ Lead 验收 → ⑤ 构建发布 → ⑥ 收尾
```

| 步 | 谁 | 动作 | 产物 |
|---|---|---|---|
| ① 取活 | Lead | 开工三步（手机指令 → `ci_checks --fast` → 现查产品数）+ 读 `docs/每日开工卡.md` §1 与队列待办 → 定今天 1–2 件，并拆成**互不冲突**的任务、标出串行点（`build.py` / DB / 发布） | 今天的任务清单 + 写作用域 |
| ② 派单 | Lead | 建共享任务（含验收标准、写权限、禁止项），用 `send_message` 派给 4 个核心工位或按需新建的工位；同时最多 2 个实现任务 | 任务板条目 |
| ③ 实现 + 自验 | 工位 | 只改自己作用域内的文件；**不 commit、不发布、不写 `site/dist`**；自验构建只能 `SITE_OUT=.tmp/<名字>` 并贴命令；按验收清单逐条给证据（before/after 数字、截图、DOM 片段） | 代码 + `reports/*.md` |
| ④ 验收 | Lead | 复核关键数字（不信口述）、跑 `ci_checks`、抽查多语/移动端、看 diff 是否越界 | 通过 / 打回重做 |
| ⑤ 构建发布 | `release` | CHANGELOG 顶部一节 → `site/build.py` 等 `== done ==` → **`sync_r2.ps1`（唯一通道）** → `verify_live --expect-version`（0 failures）→ tag/Release | 线上版本 |
| ⑥ 收尾 | Lead | 更新队列「已完成」+ `docs/交接-YYYYMMDD.md` + 开工卡状态表；该提交的提交 | 可交接状态 |

**硬规则**：工位**永不** commit / publish / 改 `site/dist`；Lead **永不**替工位写实现（除非是 P0 热修且已记录）；发布窗口内只有 `release` 能跑生产构建。

### 需求登记（硬规则，2026-11-13 用户定）

> 用户原话：「**所有提出的需求都要写进需求**」——对话里说过的需求不算落地，写进需求队列才算。

- **什么算需求**：用户消息 / 页面评审 / 手机指令 / 外部反馈 / 团队自查发现，只要提出「要做什么、要改什么、哪里不对」，都算一条需求；一条消息里有 N 个小点就拆成 N 条。
- **写到哪里**：**当天**逐条写进 `docs/谷段需求队列.md` 的「待办」，**一条一个可勾选项**，带优先级（P0/P1/P2）、所属任务号（T#）、目标版本与验收口径；**不得只留在对话里，也不得只写进 `reports/`**。
- **报告与交接的定位**：`reports/`（含 triage）只做背景、证据与复现；`docs/交接-YYYYMMDD.md` 只做跨会话摘要。**待办真相源永远是需求队列**，同一条需求在多处出现时以队列条目为准并互相链接。
- **暂缓 / 不做也要登记**：写「暂缓/不做 + 谁在何时定的 + 原因」，不删条目、不改历史（例：非 GitHub 纠错入口，用户 2026-11-13 定「先放着」）。
- **收尾核对**：收尾时逐条比对「用户当天提出的需求」与队列条目，**缺一条即视为收尾未完成**；新需求先登记再排期，不允许「先做了再说」。

## 三、并行规则（哪些能同时干）

| 资源 | 规则 |
|---|---|
| `site/build.py` | 源码同一时间只允许 **`frontend`** 一个写者（临时工位按任务 `write_scopes` 限定）；改模板的活串行 |
| `data/drugs.db` | **同一时间只允许一个写窗口**（默认 `backend` 执行）；写前备份 + manifest，写完核对产品/组件计数 |
| 生产构建 | 只有 **`release`** 能跑；构建与发布**串行**，构建期间源码冻结 |
| 只读任务 | 任意并行（审计、调研、映射表、报告）——这是并行度的主要来源，也是**按需加工位**的主要来源 |
| 发布 | 只有 **`release`** 能做，且同一时间只有一个 |

**典型并行组合**：`frontend` 改站点 + `data-scout` 做调研 + `backend` 做数据准备 + `release` 待命（构建/发布不与其他构建并行）；出现新的可并行工作 → Lead 自主加工位（不设上限），工作结束 → 自主收回。

### Lead 禁止「静止等待」子智能体（用户 2026-11-15 要求，硬规则）

> 用户原话：「**写进工作手册，静止等待子智能体太久**」。

- **禁止**用 `wait_agent` 长时间挂着空等：**单次 ≤ 5 分钟**（用户 2026-11-15 第二次收紧），且必须有理由；连续等待不得超过 **2 次**。
- 工位在实现期间，Lead **必须并行推进不冲突的事**：现查数字（SQL/产物）、跑基线与守卫（`ci_checks --fast`、`first_screen_check`）、准备 CHANGELOG/报告骨架、抽检线上页、登记队列、清理 TODO、准备发布命令。
- 判断进度靠**事实**而非等待：`list_agents`（是否 running）+ `git status` / `git diff --stat`（有没有改动）+ `team_task_list`（状态与 revision）+ `reports/` 时间戳。**不看消息就等于不知道进度**。
- 一个工位超 **30 分钟**无 diff / 无报告 / 无消息 → 立刻 `send_message` 问「卡在哪、还差什么、要不要缩范围」；超 **60 分钟**仍无产出 → `interrupt_agent` + 改派或 Lead 接管（P0 例外按 §一 记录）。
- 同一时间**最多等 1 个工位**；不要同时空等 2 个。等待期间若确实无事可做，才允许短等待（≤5 分钟），并把「在等谁、等什么、等到什么时候」写进当天的交接。
- **无事即停（用户 2026-11-15 第三次收紧，优先级最高）**：**没有用户消息、没有后台任务在跑、也没有待办要推进时，就地结束本轮，不要空转、不要轮询、不要用等待填时间。** 后台任务（构建 / 发布 / 工位跑活）完成时会自动产生新的一轮，届时再继续；用户随时发消息也随时开始新的一轮。判断标准只有三条：① 有用户消息 → 立即回应；② 有后台任务 → 等它的完成通知（**不额外轮询**）；③ 都没有 → **停**。

## 四、验收门槛（缺一条都不算完）

按改动类型（`AGENTS.md` §5）：

| 改动 | 必须做 |
|---|---|
| `etl/**` | 重跑对应 ingest → `db/check_data.py` → 条数变化同步 CHANGELOG/README |
| `lib/search.py`、归一化 | unittest + `tests/trilingual/run_tests.py`（基线 72 例 69 通过，不得新增失败） |
| `site/build.py`、页面/前端 | 全量构建 `== done ==` + **首屏守卫**（`deploy/first_screen_check.py`，改前/改后各跑一次写数字）+ 三语各抽 3 条检索 + 页数/索引/首屏体积回归 + 链接/404/sitemap 抽检 |
| 页面文案 | zh / en / es 三语同步（繁体跟随 zh-Hant 覆盖层） |
| `db/schema.sql`、`init_db.py` | 老库能直接升级（幂等），重跑 init_db 验证 |

附加（本项目踩过坑后加的）：
- **构建确定性**：同输入两次构建逐字节一致（`deploy/check_build_determinism.py`）
- **发布前全量 CI**：`ci_checks.py`（约 10 分钟，含 trilingual），不能只跑 `--fast`
- **发布后冒烟**：`verify_live.py --expect-version vX.Y.Z` 必须 0 failures
- **行尾统一 LF（2026-11-15 起）**：仓库 `core.autocrlf=false`，历史 `site/build.py` 是 **CRLF**、其余 `.py` 是 LF。v0.11.9 已把 `site/build.py` 归一为 LF；**改这个文件时不要把行尾改回 CRLF**（否则 `git diff` 会整文件 15,000+ 行、真实改动被淹没，用 `git diff -w` 才能看见）。新增/重写文件一律 LF。

## 五、发布流程（唯一入口，**单通道 R2**）

> 用户 2026-11-12 定：**站点只发布到 R2 主域 `https://drugcrossref.com/`**；git 仓库只作源码 / 文件备份，
> **gh-pages 停用**（历史分支与旧产物只作回滚参考，不再推送、不再做备份冒烟）。

```
CHANGELOG 顶部加一节（2–5 条用户能感知的变化）
  → & $py site/build.py  等到 == done ==
  → & .\deploy\sync_r2.ps1     → R2 自定义域（drugcrossref.com，增量 --checksum）
  → & $py deploy/verify_live.py --base https://drugcrossref.com --expect-version vX.Y.Z（必须 0 failures）
  → git tag -a vX.Y.Z + push tag + GitHub Release（正文用 CHANGELOG 那一节）
```

- **执行人**：生产构建 + 上线 + 线上验收由 **`release`** 一人完成（用户 2026-11-20 定「构建专门交给一个人」「发布交给别人做」）；Lead 只做验收结论与对外沟通，其它工位**不得跑生产构建**。
- **成本预算（用户 2026-11-20 定，账单截图：Class A 本周期 3.48M 总用量 / 2.48M 计费 → $13.50）**：R2 **Class A 免费 1M/月是硬上限**；单次发布 PUT 目标 ≤3,000，单次预计 >50,000 必须 Lead 批准；当月累计 >900,000 **停发布并报人/申请**；**预计会超 1,000,000（进入计费）→ 必须先向用户申请（超出 PUT / 预估美元），批准后才发，未批不得自行超支**；每次发布报告写「本次 PUT / 当月累计 / 占比」；台账 `data/r2_put_ledger.jsonl`（REL3 / T71）。
- **单通道是硬要求**：R2 是唯一发布通道，`verify_live` 0 failures 才算上线；**gh-pages 不再发布**，
  `deploy/publish.ps1`（及双击它的 `发布网站.cmd`）标注为**「历史 / 不再用于发布」**，只有回滚旧产物时由人拍板临时使用。
- **`SITE_URL` = `https://drugcrossref.com/`**：canonical / hreflang / sitemap / robots / OG 全跟它。
- **增量发布契约（v1.0.0 起，2026-11-21）**：`sync_r2.ps1` 仍是 `rclone sync --checksum`，但页面不再随版本号 / UI 变化——
  长尾页（name/drug/combo/maker/atc/cat，**147,263 页**）用稳定名 `assets/style.css` / `assets/boot.js`、页脚不写版本号；版本号只保留在顶层页。
  实测：v1.0.0 上线后**版本 +1 的增量预演 = 78 文件/版**（重构前 147,348）；sync 后另有 assets 17 文件带 `Cache-Control: public, max-age=300`。
  改 `site/build.py` 必须过 **A/A′ 0 差异 + A/B ≤500 文件（长尾六类 0 差异）**；发布前 `-DryRun` 预演 **planned ≤1,000**；旧哈希资源保活至 **2026-12-20**。
  历史参照（重构前）：v0.11.3 改了 112,796 / 121,450 个文件；v0.11.4 上传 **117,445 文件 / 868.4 MB**。
- 版本号唯一来源 = CHANGELOG 第一节；页脚 / whats-new / Release 都从它生成。
- **绝不手工改 R2 对象、绝不手工推 gh-pages**；发布中断先看 `sync_r2.ps1` 日志与 `rclone check` 结果。
- 回滚要人拍板：先 `-DryRun`，再考虑重新发布上一个 tag 的产物。
- 体积口径：**R2 免费额度 10 GiB**（gh-pages 停用后，旧的 900 MiB / 1 GB 上限不再适用）；页面性能单独看（单页 KB / `core.json` gzip）。

## 七、沟通协议

- **任务板**：每个任务写清「目标 / 验收 / 写权限 / 禁止项」；工位领取后做完标 completed。
- **回报格式**（工位 → Lead）：≤200 字「改了什么 / 怎么验的 / 还剩什么」+ 报告路径；**不贴长日志**。
- **Lead → 你**：数字与结论先行；失败和缺口照实写；需要你拍板的事单独列「需要你一句话」。
- **越界**：工位改了作用域外的文件 → Lead 打回；同一文件两人同时改 → 以任务 `write_scopes` 为准并串行化。
