## 一、编制：1 个 Lead + 8 个工位

Lead（主会话）**不写实现**：只做拆解、派单、验收、发布、对外沟通。工位是可复用的 teammate
（同一个成员可接不同任务，避免反复创建；上限 8 个）。

| 工位 | 专长 | 典型任务 | 写权限（默认） |
|---|---|---|---|
| **Lead**（主会话） | 拆解/验收/发布/文档 | 排期、审 diff、跑发布、写交接、与你沟通 | `docs/`、根级配置、发布动作 |
| **site-ui** | `site/build.py` 模板/CSS/交互 | 导航壳、首页、排版 tokens、ATC 页结构 | `site/build.py`、`reports/`、`docs/img/` |
| **atc4-ui** | 站点交互 + 数据事实表接入 | ATC4 剂型明细、结果页身份卡、分页 | `site/build.py`、`reports/` |
| **page-slim** | 构建产物与性能 | name 页瘦身、EU ingest 的 ETL 准备 | `site/build.py` / `etl/`、`reports/` |
| **search-alias** | 检索与评测 | 同物异名接入、CN 商品名数据调研 | `lib/search.py`、`tests/`、`reports/` |
| **phaseb-data** | 数据治理 | Phase B 候选、归一化映射表、`db/` 只读脚本 | `db/`（只读脚本）、`data/sources/`、`reports/` |
| **phaseb-plan** | 数据方案与评估 | Phase B 合并计划、EMA 许可评估、构建确定性 | `db/`（只读）、`reports/` |
| **alias-site** | 站点与数据衔接 | 成分页「也称」、别名表接入站点 | `site/build.py`、`reports/` |
| **pages-deploy** | 发布链路 | R2 上传 + `verify_live`、tag/Release、回滚参考 | `deploy/sync_r2.ps1`、`deploy/verify_live.py`、`reports/` |

**写权限是任务级的**：派单时在任务上写 `write_scopes`，冲突时以它为准（advisory，不是锁）。

### 主对话（Lead）只对接需求，不干活（用户 2026-11-13 定）

> 用户原话：「**主对话不负责干活，只负责对接需求**」。

- **Lead 做**：需求对接与登记（逐条进 `docs/谷段需求队列.md`）、澄清与拆解、派单、验收（跑检查/复核数字）、按固定流程构建发布、收尾文档。
- **Lead 不做**：写实现——页面 / 文案 / CSS / JS、`etl/`、数据加工、DB 写入、`site/dist` 构建产物、报告里的技术方案落地，全部由工位做。
- **唯一例外**：P0 热修（线上坏了、发布门槛被卡），Lead 可直接动手，但必须在当天交接里写明「为什么不是工位做、改了什么、怎么验的」。
- 与「工位不 commit / 不发布 / 不写 `site/dist`」合起来就是完整分工：**Lead 管流程与对外，工位管实现**。

## 二、一次交付的标准流程（8 步）

```
① 取活 → ② 拆解 → ③ 派单 → ④ 实现 → ⑤ 自验 → ⑥ Lead 验收 → ⑦ 构建发布 → ⑧ 收尾
```

| 步 | 谁 | 动作 | 产物 |
|---|---|---|---|
| ① 取活 | Lead | 开工三步（手机指令 → `ci_checks --fast` → 现查产品数）+ 读开工卡/队列/跟进提醒 | 今天做什么 |
| ② 拆解 | Lead | 把需求拆成**互不冲突**的任务；标出串行点（`build.py`/DB/发布） | 任务列表 + 写作用域 |
| ③ 派单 | Lead | 建共享任务（含验收标准、写权限、禁止项），用 `send_message` 派给工位 | 任务板条目 |
| ④ 实现 | 工位 | 只改自己作用域内的文件；**不 commit、不发布、不写 `site/dist`**；用 `SITE_OUT` 临时目录构建 | 代码 + 报告 |
| ⑤ 自验 | 工位 | 按任务里的验收清单逐条给证据（before/after 数字、截图、DOM 片段） | `reports/*.md` |
| ⑥ 验收 | Lead | 复核关键数字（不信口述）、跑 `ci_checks`、抽查三语/移动端、看 diff 是否越界 | 通过 / 打回重做 |
| ⑦ 构建发布 | Lead | CHANGELOG → `site/build.py` 到 `== done ==` → **`sync_r2.ps1`（唯一通道）** → `verify_live --expect-version`（0 failures）→ tag/Release | 线上版本 |
| ⑧ 收尾 | Lead | 更新队列「已完成」+ `交接-YYYYMMDD.md` + 开工卡状态表；该提交的提交 | 可交接状态 |

**硬规则**：工位**永不** commit / publish / 改 `site/dist`；Lead **永不**替工位写实现（除非是 P0 热修且已记录）。

### 需求登记（硬规则，2026-11-13 用户定）

> 用户原话：「**所有提出的需求都要写进需求**」——对话里说过的需求不算落地，写进需求队列才算。

- **什么算需求**：用户消息 / 页面评审 / 手机指令 / 外部反馈 / 团队自查发现，只要提出「要做什么、要改什么、哪里不对」，都算一条需求；一条消息里有 N 个小点就拆成 N 条。
- **写到哪里**：**当天**逐条写进 `docs/谷段需求队列.md` 的「待办」，**一条一个可勾选项**，带优先级（P0/P1/P2）、所属任务号（T#）、目标版本与验收口径；**不得只留在对话里，也不得只写进 `reports/`**。
- **报告与交接的定位**：`reports/`（含 triage）只做背景、证据与复现；`docs/交接-YYYYMMDD.md` 只做跨会话摘要。**待办真相源永远是需求队列**，同一条需求在多处出现时以队列条目为准并互相链接。
- **暂缓 / 不做也要登记**：写「暂缓/不做 + 谁在何时定的 + 原因」，不删条目、不改历史（例：非 GitHub 纠错入口，用户 2026-11-13 定「先放着」）。
- **收尾核对**：收尾时逐条比对「用户当天提出的需求」与队列条目，**缺一条即视为收尾未完成**；新需求先登记再排期，不允许「先做了再说」。

## 三、并行规则（哪些能同时干）

| 资源 | 规则 |
|---|---|
| `site/build.py` | **同一时间只允许一个工位改**；改模板的活必须串行，或按函数区段拆开并在任务里写明 |
| `data/drugs.db` | **同一时间只允许一个写窗口**；写前备份 + manifest，写完核对产品/组件计数 |
| `site/build.py`（构建） | 构建与发布**串行**；构建期间冻结 |
| 只读任务 | 任意并行（审计、调研、映射表、报告）——这是并行度的主要来源 |
| 发布 | 只有 Lead 能做，且同一时间只有一个 |

**典型并行组合**：1 个工位改站点 + 2 个工位做只读研究/数据准备 + Lead 写文档。

## 四、验收门槛（缺一条都不算完）

按改动类型（`AGENTS.md` §5）：

| 改动 | 必须做 |
|---|---|
| `etl/**` | 重跑对应 ingest → `db/check_data.py` → 条数变化同步 CHANGELOG/README |
| `lib/search.py`、归一化 | unittest + `tests/trilingual/run_tests.py`（基线 72 例 69 通过，不得新增失败） |
| `site/build.py`、页面/前端 | 全量构建 `== done ==` + **首屏守卫**（`deploy/first_screen_check.py`，改前/改后各跑一次写数字）+ 三语各抽 3 条检索 + 页数/索引/首屏体积回归 + 链接/404/sitemap 抽检 |
| 页面文案 | zh / en / es 三语同步（繁体跟随 zh-Hant 覆盖层） |
| `db/schema.sql`、`init_db.py` | 老库能直接升级（幂等），重跑 init_db 验证 |

附加（本项目踩过坑后加的）：
- **构建确定性**：同输入两次构建逐字节一致（`deploy/check_build_determinism.py`）
- **发布前全量 CI**：`ci_checks.py`（约 10 分钟，含 trilingual），不能只跑 `--fast`
- **发布后冒烟**：`verify_live.py --expect-version vX.Y.Z` 必须 0 failures

## 五、发布流程（唯一入口，**单通道 R2**）

> 用户 2026-11-12 定：**站点只发布到 R2 主域 `https://drugcrossref.com/`**；git 仓库只作源码 / 文件备份，
> **gh-pages 停用**（历史分支与旧产物只作回滚参考，不再推送、不再做备份冒烟）。

```
CHANGELOG 顶部加一节（2–5 条用户能感知的变化）
  → & $py site/build.py  等到 == done ==
  → & .\deploy\sync_r2.ps1     → R2 自定义域（drugcrossref.com，增量 --checksum）
  → & $py deploy/verify_live.py --base https://drugcrossref.com --expect-version vX.Y.Z（必须 0 failures）
  → git tag -a vX.Y.Z + push tag + GitHub Release（正文用 CHANGELOG 那一节）
```

- **单通道是硬要求**：R2 是唯一发布通道，`verify_live` 0 failures 才算上线；**gh-pages 不再发布**，
  `deploy/publish.ps1`（及双击它的 `发布网站.cmd`）标注为**「历史 / 不再用于发布」**，只有回滚旧产物时由人拍板临时使用。
- **`SITE_URL` = `https://drugcrossref.com/`**：canonical / hreflang / sitemap / robots / OG 全跟它。
- `sync_r2.ps1` 是增量（`rclone sync --checksum`），但**改 CSS/JS/模板时几乎所有页面都变**（样式内联进每个页面），
  增量≈准全量：v0.11.3 改了 112,796 / 121,450 个文件；v0.11.4 上传 **117,445 文件 / 868.4 MB**。发布窗口按 **30 分钟** 排。
- 版本号唯一来源 = CHANGELOG 第一节；页脚 / whats-new / Release 都从它生成。
- **绝不手工改 R2 对象、绝不手工推 gh-pages**；发布中断先看 `sync_r2.ps1` 日志与 `rclone check` 结果。
- 回滚要人拍板：先 `-DryRun`，再考虑重新发布上一个 tag 的产物。
- 体积口径：**R2 免费额度 10 GiB**（gh-pages 停用后，旧的 900 MiB / 1 GB 上限不再适用）；页面性能单独看（单页 KB / `core.json` gzip）。

## 七、沟通协议

- **任务板**：每个任务写清「目标 / 验收 / 写权限 / 禁止项」；工位领取后做完标 completed。
- **回报格式**（工位 → Lead）：≤200 字「改了什么 / 怎么验的 / 还剩什么」+ 报告路径；**不贴长日志**。
- **Lead → 你**：数字与结论先行；失败和缺口照实写；需要你拍板的事单独列「需要你一句话」。
- **越界**：工位改了作用域外的文件 → Lead 打回；同一文件两人同时改 → 以任务 `write_scopes` 为准并串行化。
