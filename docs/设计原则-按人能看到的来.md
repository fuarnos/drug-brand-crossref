# 设计原则：按人能看到的来（v1 · 2026-11-10）

> **原则原文（用户 2026-11-10 原话）**：
> 「**之后你要改成按照人能看到什么来设计**」
>
> 展开：页面不按「数据塞得下」来排，按「人一屏能看到、能操作什么」来排。
> 一屏之内必须看得到主操作和够用的条目；页头 / 筛选 / 提示 / 悬浮不许吃掉半屏；
> 字不许小到看不清；宽屏不许把正文挤成一条窄缝。
>
> 适用范围：**所有页面 / 前端 / 样式的改动**（`site/build.py`、CSS、JS、i18n 文案布局）。
> 守卫：`deploy/first_screen_check.py`（真 Chrome，4 视口 × 6 页型 × 7 指标）。
> 与 `docs/网站优化流程.md` 的关系：那个文件管「性能/体积/可访问性/SEO」，
> 本文管「**一屏里人到底能看到什么**」，是它的 §4 第 13 项。
> 数字口径：全部实测，命令与 JSON 在 §6；引用前请重跑，不要手抄。

---

## 0. 一页版

```text
改页面前：python deploy/first_screen_check.py --json .tmp/first-screen/before.json
改页面后：python deploy/first_screen_check.py --json .tmp/first-screen/after.json --baseline .tmp/first-screen/before.json
→ 报告里必须给「改前 / 改后」两列数字（AFCR / 首屏条目 / chrome / 字号），不许只说「优化了」
→ 任一指标比改前退化 >5% 要写原因；不写就回滚
```

三条不许做：

1. **不许用「数据塞得下」当理由**：一屏只能看到半行数据，再全也等于没有。
2. **不许把筛选/提示/悬浮当免费空间**：它们的位置是花掉的屏。
3. **不许靠缩字号解决拥挤**：正文 ≥16px、辅助 ≥13px 是底线（§2.3）。

## 1. 为什么（问题的形状）

用户提这条原则时给的三个现场（都能在源码/CSS 里复现）：

| # | 现场 | 实测（v0.10.1） | 现在怎么处理 |
|---|---|---|---|
| 1 | 成分页手机端筛选面板一展开就吃半屏 | `.mf-details` 打开后 `.matrix-filters` **442 px** = 844 px 视口的 **52%**；chrome 占比 0.22 → **0.70**，首屏条目 0.5 → **0** | 折叠进 `<details>`（v0.10.1 已折叠，展开仍是 442 px）→ 见 v0.10.3 排期 |
| 2 | ATC 类目页在 2560 宽屏下内容挤成一条 | 内容带 **920 px** = 屏宽 2560 的 **36%**；`.atclist` 里的行卡实测 268 px（= 屏宽 10%） | `.wrap` 宽屏放宽 + 列表改 `auto-fill` 多列（task-3） |
| 3 | 徽章 12 px、矩阵出现「三列全空」的行 | `.st-badge` / `.tag` / `.badge` 全是 **12 px**；矩阵里只在被隐藏市场有记录的规格行，可见三列全是「未收录」 | 徽章 12→13 px（task-3）；空行过滤 + 「另有 N 个规格未显示」（task-4） |

这三条的共同点：**不是数据不够，是人看不见**。所以验收不能只量「有没有」，
要量「一屏里有多少、够不够用、在哪、多大」。

## 2. 七个指标与阈值

守卫一次扫描 = **1 个页面 × 1 个视口**，量下面 7 项。视口四档：
`390×844`（手机）/ `768×1024`（平板）/ `1440×900`（笔记本）/ `2560×1440`（2K 桌面）。

### 2.1 AFCR · 首屏有效内容比

```text
AFCR = 首屏内「主内容区」面积 ÷ 视口面积
主内容区 = main 的可见矩形 ∩ 真正有内容的水平带（首屏内内容块的 x 范围并集）
          再扣掉 chrome（页头/页脚/筛选/提示/工具栏/悬浮层）
```

为什么要有「水平带」这层：宽屏下 `main` 会被 flex 撑满 2560，只按 `main` 外框算，
ATC 页那种「内容挤成 920」的毛病会被完全掩盖（会算出 0.87 的假高分）。按内容带算才是
人真正看到的宽度。

| 页型 | AFCR 阈值 |
|---|---:|
| 内容页（成分 / 名字 / ATC / coverage） | **≥ 50%** |
| 结果页（`?q=`） | **≥ 35%** |
| 入口页（首页） | **≥ 30%** |

### 2.2 指标表（口全站口径）

| # | 指标 | 口径 | 阈值 / 判定 |
|--:|---|---|---|
| 1 | **AFCR** 首屏有效内容比 | 见 §2.1 | 内容页 ≥0.50 · 结果页 ≥0.35 · 入口页 ≥0.30 |
| 2 | **主操作可见性** | 搜索框 / 筛选入口 / 首个结果操作：是否找到、是否**完整**在首屏、上缘占视口比例 | 入口页搜索框必须完整可见且上缘 **≤40%** 视口；结果页首个结果操作必须完整可见；成分页筛选入口上缘 ≤50% |
| 3 | **首屏可见条目数** | 结果行 / 矩阵行 / 卡片：可见比例 ≥90% 记 **1 条**，≥25% 记 **0.5 条** | 内容页 ≥5 · 结果页 ≥5 · 名字页 ≥1 · 入口页 不作要求 |
| 4 | **chrome 占比** | （页头 + 页脚 + 筛选 + 提示 + 工具栏 + 悬浮层）可见面积并集 ÷ 视口 | 内容页/入口页 **≤35%** · 结果页 ≤40% |
| 5 | **悬浮覆盖** | sticky/fixed 元素压在正文上的面积并集 ÷ 视口；外加「不许遮」目标（`main h1`、矩阵表头、行头、搜索框）的重叠比 | 覆盖 **≤20%** 视口；任一目标被压住 ≥25% 面积 = **遮挡违规**（表格行头这种「横向固定列」不算悬浮） |
| 6 | **字号** | 只量首屏可见文字。正文 = `p/li/td/dd/h1-h4/blockquote` 等块级内容元素；辅助 = `.sub/.meta/.tag/.badge/.st-badge/.notice/label/button/th/footer…` | 正文 **≥16px**、辅助 **≥13px**、任何可见文字 **<12px 直接违规**；`<14px` 文本占比 >50% 记 WARN（写报告，不阻断） |
| 7 | **横向溢出** | `document.scrollWidth > innerWidth`（排除设计内的横向滚动容器） | **必须为 0** |

> 指标 6 的取舍：内联小标签（`<span>/<code>/<b>`）不进正文最小值——它们的字号是继承来的，
> 拿去当「正文字号」只会把结论带偏；它们仍然进「<12px 硬门槛」与「<14px 占比」。

### 2.3 页面类型分档（一句话版）

| 页型 | AFCR | 首屏条目 | chrome | 主操作 | 字号/溢出 |
|---|---:|---:|---:|---|---|
| 内容页（`drug/` `name/` `atc/` `coverage`） | ≥50% | ≥5（名字页 ≥1） | ≤35% | 筛选/首个详情入口可见 | 全站底线 |
| 结果页（`index.html?q=`） | ≥35% | ≥5 | ≤40% | 搜索框 + 首个结果操作完整可见 | 全站底线 |
| 入口页（首页） | ≥30% | — | ≤35% | 搜索框完整可见且上缘 ≤40% 视口 | 全站底线 |

「全站底线」= 正文 ≥16px、辅助 ≥13px、无 <12px、无横向溢出、悬浮 ≤20% 且不遮正文。

## 3. 分阶段收紧（**这条最重要，别让后来人以为门禁是摆设**）

v0.10.2 的实测结果是「**全站现状**」而不是「这批改坏了」：
24 次扫描里 18 组未达标、36 项，而改前改后数字完全一样（不是回归）。
所以按阶段推进，写在任务板上、也写在这里：

| 阶段 | 做法 | 理由 |
|---|---|---|
| **v0.10.2（当前）** | **报告模式**：`deploy/first_screen_check.py` 默认只出数字、**退出码 0、不阻塞发布**；`deploy/ci_checks.py` 全量模式里记为 PASS 并在明细里带「未达标 N 项 + 最差页」；v0.10.2 验收报告出基线表 + 最差 3 页 | 存量缺口一次全红没有意义（会让门禁被绕过）；先把数字摆出来 |
| **v0.10.3** | 先修§4 的最差 3 处，再把 **「内容页 AFCR / 首屏条目 / chrome 占比 / 字号」** 四项改成阻塞（`--gate`），CI 全量模式跟着改 | 有基线才能判「退化」；修完再收紧才守得住 |
| 之后 | 新增数字只能靠 `--baseline` 判退化；不许把阈值调松来变绿（调阈值要在本文件写理由 + 版本号） | 防止用降低标准换绿灯 |

> 打开阻塞只需一个开关：`python deploy/first_screen_check.py --gate`（未达标退出码 1）；
> `ci_checks.py` 里把 `check_first_screen` 的调用加 `--gate` 即可。

**新增页面 / 新增组件从 v0.10.3 起默认按新阈值设计**（Lead 2026-11-10 决定）：不要等「以后统一改」——
新做的页型、新加的卡片/徽章/面板，提交前就要过 7 个指标（至少 390 与 1440 两档）；
新页型没进 `first_screen_check.py` 的 `PAGES` 就先加进去再改，否则等于没验。

## 5. 流程（怎么用）

### 5.1 改页面前先量

```powershell
$py = 'C:\Users\asus\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe'
# 1) 量改前（产物目录 = 当前线上构建）
& $py deploy/first_screen_check.py --json .tmp/first-screen/before.json --shots .tmp/first-screen/before
# 2) 改 build.py / CSS，重建到 == done ==
# 3) 量改后（同一套视口），并和改前比
& $py deploy/first_screen_check.py --json .tmp/first-screen/after.json --baseline .tmp/first-screen/before.json
```

- `--baseline` 会逐「页面 × 视口 × 指标」比：**任一指标退化 >5% 也算未达标**（报告里必须解释）。
- 报告里给「改前 / 改后」两列数字，**至少给 AFCR、首屏条目、chrome、最差字号**；
  截图放 `.tmp/`，需要长期留证的放 `docs/img/`（kebab-case）。
- 只扫某几页/某几个视口：`--pages drug,atc` · `--viewports 390x844,1440x900`。
- 证据模式（不参与判定）：`--expand`（筛选面板展开后）· `--scroll-probe`（滚到中部看悬浮条）。

### 5.2 与既有清单的关系

- `docs/网站优化流程.md` §4 第 **13** 项 = 本文的守卫（发布前跑，报告带数字）；
- `AGENTS.md` §5 的「页面 / 前端」一行改为：全量建站 → **首屏守卫（本文件）** → 三语抽查 →
  体积/链接/sitemap 抽检（补丁片段见 §8）；
- 和 `deploy/ui_surface_check.py`（同色守卫）是两条独立规则的守卫，都要跑：
  同色管「框里框外不能一个色」，首屏管「一屏里能不能用」。

### 6.4 已知口径与局限（引用前先看）

1. **只管首屏**：滚动之后的情况不在 7 指标里（另用 `--scroll-probe` 取证据，例如
   「滚到中部时成分页悬浮条是否还在、是否压住表头」）。
2. **不管空行语义**：「三列全空」的行会被算成条目（它确实是可见行卡），
   语义过滤由 task-4 负责；守卫只保证「条目数不骗人，空行也在数里」。
3. **不管对比度/键盘**：那是 `docs/网站优化流程.md` §2.2 的事。
4. **字体分类是启发式**：正文 = 块级内容元素；辅助 = `.sub/.meta/.tag/.badge/...`。
   分类规则写在脚本常量 `BLOCK_TAGS` / `AUX_SELF` / `AUX_ANC` 里，改规则要在这里写理由。
5. **横竖都算面积，不算密度**：AFCR 是几何面积，不区分「一行字」和「一张图」；
   所以它必须和「首屏条目数」一起看，单看会给「大空白卡片」放行。
6. **无头 Chrome 的差异**：`--headless=new` 不加载系统字体差异、无滚动条占位
   （`--hide-scrollbars`），和真机可能有 ±8px 的差；阈值留了余量，别用小数点后两位吵架。
7. **样本是一个查询**：结果页固定用 `?q=泰诺&lang=zh`；换查询条目数会变，
   要比较「首屏够不够用」时换查询要重新跑基线。
