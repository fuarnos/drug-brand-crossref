# 网站优化流程与检查清单（v1 · 2026-10-30）

> 适用：**站点/前端/文案/构建产物**的任何改动（`site/build.py`、页面、样式、i18n、SEO、可访问性、性能、发布）。
> 编写：dose-mapping（文档/审计）｜ 依据：task-31（用户 2026-10-29 问「有没有现成的网站优化流程」——采用业界权威流程，不自创）。
> 定位：本文把 **业界权威流程** 映射到本站的命令与判定值；`AGENTS.md` §5 是**门槛**，本文是**执行清单**；冲突以 `AGENTS.md` 为准。
> 外部链接查证日期：**2026-10-30**（逐条 HEAD/GET 全部 200；OWASP 旧地址 308 → 新地址，见 §1）。
> 使用顺序：**改之前读 §3.1–§3.2，改完跑 §4 的 12 项，发布后跑 §5 的 6 项**；基线数字在 §6。

## 0. 一页版

```text
① 计划（范围/是否动 build.py/是否写 DB）→ ② 基线测量（Lighthouse+体积+四套测试+sitemap/404）
→ ③ 分级 P0/P1/P2 → ④ 修复（build.py 唯一写者，串行，四语）
→ ⑤ 验收（§4 发布前 12 项，前后对比）→ ⑥ 发布（CHANGELOG→build==done==→publish→smoke→tag/Release）
→ ⑦ 发布后监控（smoke 复核/GoatCounter/search0/drift/夜间指标）与节奏（每版/每周/每月）
```

三条不可违反的纪律（详见 `AGENTS.md` §5/§6/§7）：

1. **同一时间只有一个会话跑 `site/build.py` 或 `deploy/publish.ps1`**；`site/build.py` 是唯一写者，构建期间冻结。
2. **发布只走 `deploy/publish.ps1`**；不手工推 `gh-pages`、不手工改 `site/dist/`。
3. **数字以实测为准**：文档/页面里的旧数字不能直接引用（本流程 §6 给出 2026-10-30 基线；每次发布后更新）。

## 2. 标准（本站采纳的门槛）

### 2.1 性能与体积预算

| 指标 | 2026-10-30 实测（v0.9.0） | 预算 / 判定 |
|---|---:|---|
| Lighthouse 移动端四项（首页/成分页/名字页/atc） | **未测**（v0.9.1 task-22 建基线） | **四项 ≥ 90**；未达标必须写「差距 + 原因 + 跟进任务号」，不得静默放行 |
| LCP / CLS / INP（lab） | 未测 | **LCP < 2.5s、CLS < 0.1、INP < 200ms**（Lighthouse 的 TBT < 200ms 作代理） |
| 首屏资源（HTML+CSS+i18n+bilingual+app，未搜索） | **311 KB raw / 104 KB gz** | ≤ 330 KB raw / ≤ 110 KB gz |
| 首搜索引 `core.json` | **35,790,720 B raw / 8,676,313 B gz** | raw ≥ 10 MB（publish 门槛）；gz ≤ 9.5 MB |
| 首搜前缀分片（`data/idx/shard-*.json`，99 个） | 中位 **1.04 MB raw**、最大 1.10 MB | 单分片 ≤ 1.2 MB raw |
| 名称明细桶（`detail-*.json`）/拼音表 | 最大 **4.16 MB** / **3.08 MB** raw | 按需加载；体积变化需在报告说明 |
| 单页 HTML 平均 | **5,067 B** | ≤ 6 KB（薄页 noindex 另案） |
| `site/dist` 总量 | **116,883 文件 / 770.8 MB** | ≤ 810 MB；超过必须说明（如全量单包装名字页另案，需先评估 800 MB 守卫） |
| 构建耗时 | **2.92 分钟**（`== done ==` exit 0） | ≤ 5 分钟；超过需在报告解释 |
| sitemap | **68,430 URL** | = HTML 116,717 − noindex 48,287（公式校验，见 §4-11） |

> 预算口径：**基线 + 约 5% 余量**，随版本更新（§6）。任何超预算必须写进报告/CHANGELOG 说明，不能只靠人记。

### 2.2 可访问性（WCAG 2.2 AA 基础）

- **Lighthouse Accessibility ≥ 90**（移动端）+ **WAI Easy Checks 逐项人工抽查**（标题、alt、标题层级、对比度、文字缩放、键盘可达、焦点可见、表单标签、语言、无键盘陷阱、结构）；
- 具体到本站的硬项：搜索框有 `label`/`aria-label`；正文对比度 ≥ 4.5:1、非文本对比 ≥ 3:1；触控目标 ≥ 24×24（推荐 44×44）；每页一个 H1；`<html lang>` 正确；键盘可完成主流程（搜索→结果→成分页→矩阵筛选）；移动端表头语义不丢（不要 `display:none` 掉唯一表头）。
- 只做「基础项抽查」，**不宣称全站 WCAG 合规**；问题记录在报告，P0/P1 按 §3.3 分级。

### 2.3 SEO / 可发现性

- 可抓取：`robots.txt`、`.nojekyll`、无构建阻断；
- `sitemap.xml` 覆盖全部应索引页；**noindex 页不进 sitemap**（当前薄页 48,287：单包装名字页 + 单产品厂家页）；
- canonical、hreflang（en/es/zh/zh-Hant + `x-default`）四语一致；404 页能回站内；
- 结构化数据：站点级 `WebSite`/`MedicalWebPage`，数据产品 `Dataset`（task-23）；
- 标题/描述唯一且本地化（四语）。
- 参考：[Google Search Essentials](https://developers.google.com/search/docs/essentials)。

### 2.4 安全与隐私

- **GitHub Pages 限制**：不能自定义响应头（CSP/HSTS 等大多不可控）→ 在报告记录「不可做项 + 已做项」，用 [OWASP Secure Headers](https://owasp.org/projects/secure-headers-project) 做清单核对；
- 外链 `rel="noopener"`；不引入第三方脚本（GoatCounter 除外）；无内联可疑脚本；
- 隐私：GoatCounter **cookieless**（不写 cookie、不存 IP/UA，见 [隐私说明](https://www.goatcounter.com/help/privacy)）；`localStorage` 只存 UI 偏好（矩阵列记忆）；About 有四语隐私说明；
- 不记录个人数据；报告中的搜索词只保留药名（task-30 已验证）。

### 2.5 内容与四语

- 四语 **zh / en / es / zh-Hant 同步**（i18n key 对齐，构建期断言）；品牌名**永不翻译**；
- plain language（GOV.UK/USWDS 做法）：每页一个 H1、术语一致、错误/空状态给「下一步动作」；
- 页面数字与 `data/drugs.db` 现查一致（README/About/CHANGELOG 同口径）；
- 文案改动**必须四语一起**，不能只改一种。

### 2.6 底线（优化不能交换的东西）

优化不得违反 `AGENTS.md` §1：商品名不是主键、查询永远返回候选集、碰撞自动推导、只做身份对应与「不可互换」警示、**不给用药建议/不做剂量换算**。任何以分数/流量为名削弱这些语义的改动一律拒绝。

## 3. 阶段（7 步闭环）

### 3.1 计划

- 写清：改什么（文件/页面/i18n/SEO）、影响面（是否动 `site/build.py`、是否写 `data/drugs.db`）、验收标准、发布版本号。
- 动 DB → 先走 DB 窗口（备份/回滚清单/`check_data`）；动 `site/build.py` → 确认没有其他会话在构建（§0 纪律 1）。
- 排期参考：UX 审计 P0（`reports/ux-audit-20261030.md`）> Lighthouse/WCAG（task-22）> 数据/内容 > 体验余项；真实行为数据目前样本≈0（`reports/user-evidence-20261030.md`），**不作为降级 P0 的理由**。

### 3.3 分级（P0 / P1 / P2）

| 级别 | 判定 | 本站例子（来自 UX 审计/数据审计） |
|---|---|---|
| **P0（立即修）** | 身份/数据错误、主流程不可用、移动端首屏无反馈、安全/隐私、发布阻断 | 同成分表混入不同成分（C-1）；品牌查询看不到品牌（C-2）；移动端结果区 y=935（F-1）；矩阵筛选死按钮（M-1/C-7）；构建不完整 |
| **P1（下一批）** | 可用性/无障碍/i18n 系统性缺陷、性能预算超标 | 名称页英文表头（C-4）；H1 混入版本号（C-5）；ATC 中英拼接（C-6）；对比度/触控目标（W-2/W-3）；Lighthouse < 90 |
| **P2（backlog）** | 体验优化、内容打磨、非关键性能 | 零结果/404 增强（E-1/E-5）、结果页长度、筛选器排序 |

> 规则：P0 当版修；P1 下一批；P2 进队列。判断「影响 × 成本」，不逐项问用户（`AGENTS.md` §7 triage 规则）。

### 3.4 修复

- `site/build.py` 唯一写者；不要多人同时改；每次改完 `& $py -m py_compile site/build.py`。
- 本地预览 `& $py serve.py 8000`（或 §3.2 的 8123），前后截图存 `.tmp/<topic>/`；需要入库的截图放 `docs/img/`（kebab-case）。
- 文案四语同步；样式改动先搜现有常量（`site/build.py` 内联生成，别另起一套）；不改生成物。
- 数据/DB 改动另走窗口（备份 + 回滚清单 + `db/check_data.py`）。

### 3.5 验收

- 跑 §4 的 **12 项**，记录 before/after（Lighthouse 分数、体积、测试计数、截图）。
- 门槛：P0 全部关闭；P1 有明确归属版本；超预算项有解释与跟进任务；四套测试无新增失败。

### 3.6 发布（唯一入口，见 `AGENTS.md` §6）

1. `CHANGELOG.md` 顶部加 `## vX.Y.Z — YYYY-MM-DD`（2–5 条用户可感知变化）；
2. `& $py site/build.py` → 等 `== done ==`；
3. `powershell -NoProfile -ExecutionPolicy Bypass -File deploy\publish.ps1`（增量；失败保留临时目录，自动回滚）；
4. `& $py deploy/verify_live.py --expect-version vX.Y.Z`；
5. `git tag -a vX.Y.Z` + push + `& $py deploy/github_release.py --tag vX.Y.Z --name "vX.Y.Z - 一句话"`。

> `publish.ps1` 自带检查：`index.html` 存在、`data/idx/core.json` ≥ 10 MB raw（过渡期 `data/index.json` ≥ 5 MB）、文件数 ≥ 24,000、无 0 字节、**拒绝在 15 秒内新写入或 `build.py`/`run_all.py` 仍在跑时发布**（见 `DEPLOY.md`）。

### 3.7 发布后监控

- **smoke 复核**：`verify_live.py` 的 `failures: []` 与 live 版本；
- **真实行为**：GoatCounter（PV/来源/搜索词/`search0-*`）；注意样本小（2026-10-30 报告仅 103 hits，见 `reports/user-evidence-20261030.md`），**流量门槛**：≥1,000 PV、≥300 搜索事件再谈需求结论；
- **数据源漂移**：`etl/drift_check.py`（task-25，待建）+ 夜间指标 `db/nightly_metrics.py`；
- **性能**：每月用 PSI/Lighthouse 复测一次线上关键页，与 §6 基线对比。

## 7. 紧急热更新例外（静默发布）

允许「不发版、不写 CHANGELOG/tag」的例外，仅限：

- 根目录第三方验证文件（如 `e2fea3df…txt`）等**纯静态、无用户可见变化**的文件；
- 合规/安全紧急文案（如「国家和地区」措辞修复，2026-10-29 已发生）；
- 线上 404/整站不可用类事故的止血。

执行要求（缺一不可）：

1. 仍走 `site/build.py` 到 `== done ==` + `deploy/publish.ps1`（**不手工推 gh-pages、不手工改 dist**）；
2. 发布后仍跑 `verify_live.py`（版本号可不变，确认 `failures: []`）+ 线上抽查；
3. 留痕：`reports/` 写一页（改动/原因/证据），并通知 Lead；
4. 24 小时内补齐文档（队列/交接），不占版本号、不进 What's new。
